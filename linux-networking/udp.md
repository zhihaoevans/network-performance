# UDP：PPS、丢包与接收效率

UDP 不提供 TCP 式的可靠交付；测试成功发送多少不等于应用成功收到多少。应分别记录发送提交数、实际发出数、接收数、序列号缺口、乱序和重复。

## 把丢失位置分开

| 层次 | 观察 | 下一步 |
| --- | --- | --- |
| 发包器 | 实际速率低于设定值 | 看发送线程、系统调用和节奏控制 |
| 链路/网卡 | CRC、missed、per-queue drop | 看链路质量与队列服务速度 |
| 协议/socket | UDP RcvbufErrors 等增量 | 看应用读取和缓冲策略 |
| 应用 | 内部队列满、校验失败 | 看业务处理与工作分配 |

字段含义要按当前内核与驱动确认。UDP InErrors 与其子类可能重叠，不能直接求和当总损失。

## 包长与分片

先使用不会超过已验证 PMTU 的数据报。大数据报可能受到分片、PMTU 错误和重组资源影响，丢失一个分片即可导致整个数据报无法交付。读缓冲区过小还可能截断数据报，应用应检查返回长度和 MSG_TRUNC。

## 应用优化顺序

1. 明确数据报最大长度，保证接收缓冲与解析逻辑正确。
2. 把高开销日志、分配和复杂业务从接收热路径分离。
3. 比较 recvmmsg/sendmmsg 批量调用与逐包调用。
4. 为批量设置上限，避免一直等待凑满导致延迟增长。
5. 若使用多 socket/线程，验证流量实际分配与包序要求；不能假设平均分配。
6. 只在证据指向 socket 缓冲不足时扩大缓冲，并观察内存与排队延迟。

## 实验矩阵

保持总 offered load 不变，分别改变包长、流数、接收线程数、批量大小。每组记录实际发送和接收 PPS、丢包、每核 CPU、应用处理时间。对“相同 bit/s、不同包长”尤其要观察 PPS 的变化。

参考：[udp(7)](https://man7.org/linux/man-pages/man7/udp.7.html)、[recvmmsg(2)](https://man7.org/linux/man-pages/man2/recvmmsg.2.html)。实践：[负载与包长实验](../labs/003-udp-packet-size.md)。

# 测量设计与结果可信度

## 测量边界

发送器提交成功、网卡发出、对端网卡收到、应用消费完成是不同事件。选择吞吐、丢包或延迟指标前先定义边界；硬件计数器与应用字节数不能未经换算直接相减。

| 要素 | 必须固定或记录 |
| --- | --- |
| 负载 | 协议、帧长分布、连接/流数、方向、到达模式 |
| 数据 | 随机或重复、是否可压缩、是否命中缓存 |
| 时间 | 预热、稳定测量、冷却、重复次数 |
| 系统 | CPU 频率、NUMA、后台任务、工具版本 |
| 功能 | 校验、加密、过滤、日志、conntrack 与 offload |
| 误差 | 时钟同步、采样频率、计数器重置与溢出 |

## 开环与闭环

闭环客户端往往完成一个请求再发下一个。服务变慢时，客户端也降低提交速度，可能掩盖排队风险。开环按照预定到达时间提交，更适合观察过载行为，但需要记录客户端是否跟得上计划。

这不是二选一：真实场景可能混合两种行为。报告应说明负载模型，避免把闭环测得的低延迟外推到固定到达率场景。

## 分位数与失败样本

保留原始样本或可合并的直方图。不同运行的 P99 平均值不是合并 P99。超时、拒绝和发送失败单独统计，并说明其是否参与延迟分布。只统计成功请求可能把系统过载后的体验画得过于乐观。

单向延迟需要知道时钟误差；没有可靠时钟同步时可测 RTT，但不能把 RTT/2 当作已经测得的单向延迟。

## 重复、统计与对比

至少三次是起步，不是统计可靠性的保证。保留所有运行，报告样本数、中位数和范围；波动大时先查环境，再增加重复。比较两个配置时使用相同流量、同一观测窗口，尝试 A/B/A 或交替执行。

网卡包速率可以由两次计数差除以时间差得到。若计数倒退，先检查重置、接口重建或溢出，不能直接得出负速率。

## 发包器也需要验证

测得的平台上限可能是客户端 CPU、PCIe、流量生成逻辑或计时器上限。观察发送端实际 TX、接收端 RX 与流量发生器报告的一致性。测试转发器时，最好让产生流量和接收校验的负担位于独立机器。

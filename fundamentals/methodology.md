# 性能分析方法：从目标到证据

类型：工程方法。本文的流程是仓库建议，不是已执行实验。

## 先写出可判断的目标

“网络慢”不是目标。把需求写成：在指定帧长/请求大小、并发与流数下，接收有效吞吐量达到某个值，同时 P99、错误率和 CPU 不超过约束。定义双向还是单向、短连接还是长连接、冷启动还是稳定态。

| 场景 | 主要指标 | 必须一起记录 |
| --- | --- | --- |
| 大文件传输 | 接收 Goodput | RTT、重传、端点 CPU、磁盘是否参与 |
| 防火墙转发 | PPS、无丢包速率 | 帧长、流数、规则数、功能开关 |
| RPC 服务 | 成功请求率、P99 | 超时、请求大小、到达速率、并发 |
| 建连服务 | CPS、握手延迟 | 连接存活时长、TIME_WAIT、错误类型 |
| 低延迟行情 | 单向/往返延迟 | 时间戳位置、时钟误差、负载与丢包 |

## 分层定位顺序

1. 确认测试有效：发送器是否达到了目标速率？计数器窗口是否一致？
2. 确认物理路径：端口速率、双工、错误、MTU、中间设备与路径变化。
3. 观察 CPU/队列：单核是否饱和、队列是否不均、上下游是否有积压。
4. 检查传输层：窗口、重传、RTT、拥塞控制、socket 等待。
5. 分析应用：锁、内存分配、系统调用、序列化、加解密和下游依赖。
6. 提出可以推翻的假设，再做单变量改变。

## 用证据连接假设与操作

| 观察 | 候选解释 | 验证方式 | 不能直接推出 |
| --- | --- | --- | --- |
| 多连接快、单连接慢 | 单流队列或窗口约束 | 看各队列、每核与 TCP 状态 | 必须开 RPS |
| CPU 总利用率低 | 一个关键线程已满 | 每线程与每核采样 | CPU 不是瓶颈 |
| RX drop 增长 | 某接收层资源不足 | 驱动、协议、socket 分层计数 | 网线有问题 |
| P99 高而平均低 | 排队、调度或偶发慢路径 | 相关时间窗口追踪 | 增大缓冲能解决 |
| 开启日志后变慢 | I/O、锁或格式化开销 | 采样、短窗口关闭非必要日志对比 | 日志一定是唯一根因 |

## 变更闭环

建立基线 A → 变更 B → 恢复 A。交替执行 A/B，避免温度、后台负载或流量漂移被误当收益。每次写下原值、改值、恢复命令与退出条件。

优先优化真正约束目标的部分。假设只有 30% 时间可被加速，即使那部分无限快，整体理论加速上限也只有 1/0.7≈1.43；这是 Amdahl 模型估算，前提是其余工作与负载不变。

## 一份结论应该包含

目标、环境、负载、基线、干预、结果波动、失败结果、代价、适用范围、原始记录。复盘中区分“相关”“支持假设”和“证实原因”。

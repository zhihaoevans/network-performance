# TLS、QUIC 与加密网络性能

## 分开测量

| 工作负载 | 主要成本 | 测量方式 |
| --- | --- | --- |
| 新建 TLS 连接 | 握手、证书与密钥运算 | 握手成功率、延迟、CPS |
| 长连接传输 | 对称加密、记录组织、I/O | Goodput、CPU、记录大小 |
| 会话恢复 | 恢复路径及状态管理 | 与完整握手分组对比 |
| QUIC 多流 | 用户态传输、加密、调度 | 每流延迟、丢失恢复、连接 CPU |

算法、库、CPU 特性、协议版本与数据大小必须记录。不能用明文 TCP 的 CPU 成本预测 TLS 服务。

## QUIC 不只是“更快的 UDP”

QUIC 自己实现可靠传输所需的丢失恢复和拥塞控制。比较时对齐业务语义、连接复用、RTT、丢包、加密和流并发；不能把裸 UDP 与可靠 QUIC 当作等价工作量。

多流可减少某些跨流的有序交付阻塞，但仍共享连接/路径资源，拥塞、CPU 和应用锁不会自动消失。

## 加速路径

先确认热点是否在密码运算、内存复制、系统调用还是应用。Kernel TLS 可将支持的 TLS 数据路径处理交给内核，握手仍需相应用户态支持；硬件卸载能力需要具体设备与驱动配合。每种加速都验证协议兼容和回退路径。

## 实验要求

分别测试冷握手、恢复握手和长连接；固定密码套件、证书链、请求/响应长度。记录 CPU cycles/byte、失败率、握手 P99 与连接内请求 P99。不要关闭安全校验制造不可比结果。

参考：[Kernel TLS](https://docs.kernel.org/networking/tls.html)、[RFC 9002](https://www.rfc-editor.org/rfc/rfc9002.html)。
